Building TaskFlow: From Idea to
150+ Beta Users in 3 Months

A deep dive into how I co-founded a student project management tool — the technical decisions, the mistakes, the pivots, and what we learned about building for a niche audience.

Mifzal Fawwaz

CS Student & Founder

May 28, 2025 8 min read 3,241 views 148 likes
#React #Node.js #MongoDB #Startup #ProductDev
Share

TL;DR

We built TaskFlow — a project management tool for students — in 3 months, reached 150+ beta users, and learned invaluable lessons about product-market fit, full-stack architecture, and entrepreneurship. This post covers everything.

It started with a frustration. My team and I were constantly switching between Notion, WhatsApp, and a shared Google Doc to manage our university group projects. We were CS students — surely we could build something better. So we did.

TaskFlow began as a weekend hack. Three months later, it had 150+ active beta users, a waitlist, and had been featured in our university's tech newsletter. Here's the full, unfiltered story of how we built it.

01 The Problem We Were Solving

We surveyed 40 students across 6 departments and found a consistent pattern: group project management was painful. The core issues were:

  • Fragmented communication across too many platforms
  • No deadline visibility for all team members simultaneously
  • Existing tools like Jira and Asana were too complex for academic contexts
  • No integration with university submission portals or calendars

The insight was clear: students needed a lightweight, opinionated tool built specifically for academic project workflows — not a watered-down enterprise solution.

02 Technical Architecture

We chose a MERN stack (MongoDB, Express, React, Node.js) for the core application. Here's how our architecture looked after the first major iteration:

Frontend
  • React 18 + Vite
  • Tailwind CSS
  • React Query
  • Socket.io Client
Backend
  • Node.js + Express
  • REST API
  • Socket.io Server
  • JWT Auth
Data & Infra
  • MongoDB Atlas
  • Redis Cache
  • Vercel + Railway
  • Cloudinary

One of our biggest technical decisions was implementing real-time collaboration via WebSockets. Here's the core socket setup we used for task updates:

socket.js
// Real-time task update handler
io.on('connection', (socket) => {

  // Join a project room
  socket.on('join-project', (projectId) => {
    socket.join(projectId);
    socket.emit('joined', { projectId });
  });

  // Broadcast task updates to all team members
  socket.on('task-update', async (data) => {
    const updated = await Task.findByIdAndUpdate(
      data.taskId,
      data.updates,
      { new: true }
    );
    io.to(data.projectId).emit('task-updated', updated);
  });

});

03 The Pivot That Changed Everything

At week 6, we had 20 users and almost zero engagement. Our original vision was a full-featured project management suite. We were wrong about what students actually needed.

Key Insight

Students didn't want a project management tool. They wanted a deadline accountability system with built-in team notifications. We stripped 60% of the features and rebuilt around this core insight.

After the pivot, we launched a stripped-down v2 in 2 weeks. The results were immediate: daily active users went from 4 to 47 within the first week of the new release.

04 Growth: 0 to 150+ Users

We didn't run ads. Our entire growth was word-of-mouth, campus ambassador outreach, and one well-timed Reddit post. Here's a breakdown of our acquisition channels:

63%
Word of Mouth
24%
Campus Outreach
13%
Reddit / Social

The Reddit post on r/cscareerquestions titled "I built a project management tool for CS students — here's what I learned" got 847 upvotes and drove 60 sign-ups in 48 hours. Authentic storytelling beats any ad spend.

05 Key Lessons & Takeaways

Talk to your users before writing a single line of code

We wasted 3 weeks building features nobody asked for. User interviews are the most valuable engineering time you'll spend.

Simplicity is a feature, not a limitation

Stripping 60% of our features doubled our engagement. Constraint breeds clarity.

Ship early, iterate fast

Our v1 was embarrassingly rough. But the feedback we got in week 1 was worth more than any amount of pre-launch polish.

Document everything publicly

Writing this blog post drove more sign-ups than any feature we shipped. Building in public is a growth strategy.

06 The Task Schema That Evolved

Our MongoDB task schema went through 4 iterations. Here's the final version that supported all our core features:

Task.model.js
const taskSchema = new Schema({
  title:    { type: String, required: true },
  status:   { type: String, enum: ['todo', 'in-progress', 'done'] },
  assignee: { type: ObjectId, ref: 'User' },
  deadline: { type: Date, required: true },
  project:  { type: ObjectId, ref: 'Project' },
  tags:     [String],
  priority: { type: String, enum: ['low', 'medium', 'high'] },
}, { timestamps: true });

We're working on a calendar integration, a mobile app, and exploring a freemium model. If you're a student and want early access, drop your email below.
